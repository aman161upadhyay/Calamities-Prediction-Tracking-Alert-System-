# Three operational briefs

Supply real schema, approved records, permission rules, stack/version and tokens. These examples adapt research 05 and are untested. No example authorizes live data access.

## Pipeline workbench

```text
Create a pipeline workbench for a five-person B2B team to identify deals needing
a next action today. Use supplied schema and authorized records.
Fields: company, deal title, owner, stage, value/currency, next action,
next-action date and last contact. Ask about missing fields or permissions.
Desktop: compact object navigation, saved-view selector, filter/sort toolbar,
48px starting rows and right-side detail panel. Right-align values and use the
user's timezone. Study Twenty record views and Attio object clarity without
copying branding. Use neutral surfaces and one brand action colour.
No decorative gradients or oversized KPI row.
Specify row-open versus checkbox selection, bulk ownership scope, inline-stage
edits, undo and server validation. Include no matches, first-use empty,
loading, read-only and failed-save states. Preserve filters in the URL.
Test keyboard and an appropriate narrow-screen replacement.
Never invent deal values or send external emails.
```

## Support operations

```text
Design a support operations page for a manager reviewing morning queues.
Decision: which queues need staffing changes. Use supplied aggregates with
freshness and metric definitions. Show backlog, oldest waiting ticket and
breached response commitments with units and comparison periods.
Put the queue table before secondary charts. Start with readable compact
operational text and tabular numerals. Use explicit status text and non-colour
warning indicators. Queue rows open ticket lists. Charts have data alternatives.
Study Linear's focused work surface, not its brand.
Include stale data, partial data, denial and refresh failure without wiping
the last successful result. Offer manual refresh with pending status.
No count-up animation, invented upward trends or arbitrary pie charts.
Deliver responsive views and keyboard evidence. Mark unavailable checks.
```

## Customer renewal

```text
Build a renewal detail page for an account manager preparing a call.
Use supplied customer data and permissions. Header: account name, owner,
renewal date and “Prepare renewal”. Content: contractual facts, product usage
with period/source, open issues, contact history and next steps.
Prioritize actionable risk explanations over a decorative score.
Use two desktop columns and a readable activity timeline. On mobile put renewal
facts and next action first. Follow existing tokens and components.
Include long names, missing contacts, restricted financial fields, no activity
and failed-note-save recovery. Timeline markers indicate actual time ordering.
Do not infer churn probability or invent usage. Confirm before any email or
contract modification. Test recovery and report actual checks.
```

Acceptance: decision fit, explicit state truth, recoverable actions and accessible density. Failure modes: fake metrics, ambiguous selection and success before persistence.
